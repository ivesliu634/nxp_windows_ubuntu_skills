# NXP Windows + Ubuntu Server 当前系统架构

状态：待逐节审阅的初稿，尚未作为已确认设计定稿。

本文说明 Windows + Ubuntu server 工作区的组织方式、职责和边界，
包括 Agent 与技能、资源与执行工具、case 证据和知识沉淀。

这是供维护者共同审阅的架构说明，不是 Agent 必读入口或施工手册。
职责说明不等于远端已经部署同一版本，也不证明业务构建或板级运行已经通过。

## 1. 系统定位

本工作区不是把源码、SDK、工具链、镜像和 case 都装进 Git 的完整环境备份。
它是面向 NXP i.MX 工程任务的轻量方法、规则、资源入口与工具维护仓库。

工作区由控制面、两端资源与执行面，以及远端工具的维护/部署源组成：

- `workspace`：Windows 上的工作区约定、按需技能、本机配置和架构文档。
- Windows `support_level`：资料、板级知识、板级工具和完整 case。
- Ubuntu 资源与执行端：业务源码、SDK、工具链、固定固件和构建现场。
- Windows `server`：远端需要的小文件的维护/部署源，不是 Ubuntu 资源实体的本地副本。

系统服务于两个长期目标：

1. 使用已有工程资源完成当前任务，并保留可核对的输入、动作、产物和观察。
2. 从真实 case 提炼可复用知识，经审阅后进入长期说明、规则或工具。

Agent 仍使用自己的任务理解、计划、工具使用和技能读取机制。
工作区补充领域能力和工程约束，不为 Agent 再实现一套工作流。

## 2. 总体设计思路

围绕当前未解决问题推进，不默认跑完整条链，
也不通过全局技能目录、固定加载顺序或模拟 owner 交接来驱动任务。

实际任务可以只涉及讨论、资料查询、源码修改、构建、上板或客户交付中的一部分。
Agent 按当前任务需要读取相关技能与资料；不能因为资源已找到，就自动扩大到构建或烧写。

关键设计原则：

- 基准优先：先确认当前环境下可信的参考状态，再引入必要改动。
- 最小增量：保护已有修改，已验证正常的部分不因当前猜测而改动。
- 证据分层：文件存在、构建成功、传输成功、启动和业务运行分别证明。
- 资产与任务分离：共享基线用于阅读和对比，任务修改与构建在 case 现场完成。
- 已知风险按需硬化：工具检查明确的输入和执行约束，不把所有工程判断写死。
- 设计、操作、本机配置与任务事实分开维护，避免重复说明互相漂移。

用户仅要求讨论、查资料、改代码或提供命令时，不自行构建、取回或上板。
完整执行链只能在实际需要且已授权时展开；它不是固定任务模板。

## 3. 分层架构

### 3.1 原生 Agent 与工作区约定

仓库的 [Copilot 指令文件](../../.github/copilot-instructions.md) 引用
[AGENTS.md](../AGENTS.md)。后者表达始终适用的工作区约定：
两端分工、授权范围、保护已有修改、工程判断、证据和发布边界。

它不维护技能目录、不指定总入口，也不介绍一套由技能组成的调度层。
需要实际路径、连接或工具位置时，才读取非公开的本机配置 `workspace\ENVIRONMENT.md`。

### 3.2 按需领域技能

领域能力以按需技能提供。
技能由 Agent 自身机制发现和加载，名称与描述表达适用任务，正文提供具体方法和检查要求。
技能是指导材料，不是独立执行的 Agent。

以下说明现有材料的职责，不表示先后顺序或派发关系：

| 技能 | 领域方法 |
|---|---|
| `understanding` | 拆分概念混淆，区分现象与根因，明确证据缺口与最小区分实验 |
| `support` | 定位资料、源码、SDK、工具、固件和已有 case，核对资源用途与缺失条件 |
| `myserver` | 使用已有 SSH/SCP 操作 Ubuntu，处理执行位置、跨 shell 命令与文件传输 |
| `compile` | 确认构建对象与最小输入，使用项目方法和构建工具，核对构建记录与产物 |
| `board-exec` | 核对真实板型与阶段，按授权操作板控、USB、串口与写入工具，保留动作前后证据 |
| `build-customer-release` | 从 case 证据组织客户包、核验补丁和脚本，区分已验证与未验证声明 |

`understanding` 与其他技能平级，不承载所有任务都必须加载的全局原则。
具体项目手册、工具参数和较长专题按需查阅，不全部塞进技能正文。

### 3.3 支撑资源层与两端位置

支撑资源按工程职责分类，并按资源和执行特点分布：

| 资源或现场 | Windows | Ubuntu server |
|---|---|---|
| 工作流维护 | Agent 使用的约定、技能、本机配置与工作流 Git | 不部署 AI 工作区或本工作流 Git |
| 资料与长期镜像入口 | RM、原理图、BSP 文档、镜像资料 | 不保留 Windows 资料目录副本 |
| 业务代码与构建输入 | 不 clone 业务源码或取回整棵源码/缓存 | 源码、协同工作区、SDK、release 包、工具链与固定固件 |
| 执行工具 | BCU、UUU、串口、USB 与 RM 查询工具 | 构建工具与客户包校验器 |
| 任务现场 | 完整 case、板级原始日志与所需交付文件 | 同名 case 的业务源码和构建现场 |
| 待归纳知识 | `to_absorb` 及其来源 case | 不创建同用途副本 |

Windows 仓库的结构是：

```text
<仓库根>\
  .github\copilot-instructions.md
  workspace\
    AGENTS.md
    ENVIRONMENT.md
    .agents\skills\
    docs\
  support_level\
  server\
    README.md
    support_level\
```

目录可整体重命名，不能把当前资料包根名称写成通用路径。
Ubuntu 的真实资源根、已有源码位置和执行现场由本机配置登记，
不要求所有资源都位于一个固定名称的目录。

分类入口见 [Windows 资源说明](../../support_level/README.md)、
[server 资源说明](../../server/support_level/README.md)。

### 3.4 对象旁的关系索引

分布式 `RELATION.yaml` 在对象旁保存说明入口、稳定关联、case 要求和 warning。
它是定位资料的索引，不是新知识库、自动执行引擎或技能调度机制。

索引中的 `owner` 是分类字段，不代表独立 Agent，也不授权执行动作。
关系中的候选项目不自动成为本次全部依赖，历史关联也不证明资源已齐备或当前实物已连接。

当前按需读对象旁的关系文件，不为本架构引入中心 catalog、关系聚合服务或额外调度系统。
索引与说明不一致时，核对对应说明、机器规则和原始来源，不以 YAML 外观替代证据。

### 3.5 执行工具

工程门禁区分判断、检查与执行：

- 项目决定技术能力与实际构建方法。
- Agent 明确本次目标、输入、修改范围及理由。
- 工具按已有规则检查、展示、绑定和执行计划，记录实际结果。

`compile-tool` 在 Ubuntu 执行。项目公开清单由工具生成内部 manifest/request，
显式请求入口才由 Agent 维护这些记录；同一任务不重复手填两套。
命令模板来自项目 profile，通用请求的命令来自项目方法与显式计划。

工具检查来源、参数、路径、产物身份、已声明依赖以及 prepare/run 一致性。
它不自动决定是否重编或推断全部项目依赖，也不能从主机权限层阻止故意调用裸构建命令。

imx-mkimage 不以历史 recipe/固件矩阵作为默认能力白名单。
有界源码解析和 M payload 核验不等于完整理解 GNU Make 或证明发布兼容性，
完整输入及版本适配仍须根据本次源码和发布资料核对。

详见 [compile-tool USAGE](../../server/support_level/tools/compile-tool/USAGE.md)。
Windows 板级工具负责实际操作与采集，不能仅凭命令成功宣布板状态推进；
客户包校验器负责发布内容检查，不能替代缺失的板级运行证据。

## 4. 代码与构建资产模型

这些资产与实际业务源码都在 Ubuntu。Windows `server\support_level` 只维护小型说明与规则，
不能把本地同名目录当成已取得源码或可执行的构建现场。

### 4.1 `code_assets/projects`

单项目 Git 仓库或 manifest 的共享基线，用于源码阅读、版本核对和准备任务副本。
例如 ATF、U-Boot、SMFW、imx-mkimage、Linux 或 MCUX SDK 相关源码。
具体项目是否已经取得、当前 ref 和已有修改都须现场核对，名称列表不是安装证明。

源码参考与 release 编译来源分开：MCUX SDK 源码或 manifest
不能仅凭存在就替代本次需要的 SDK 发布包。

### 4.2 `software_stacks`

跨项目软件线的说明，与 `code_assets` 同属资源根下的独立分类。
例如 RTE 对 LF 家族、源码 ref、release 包和启动镜像内容的组合要求。
软件线名称不能直接决定某个 imx-mkimage recipe。

### 4.3 `code_assets/workspaces`

只有整体协同才有意义的多仓工作区，保留仓库间版本和构建关系。
现有分类包括 HMC 和 Zephyr 工作区；某个工作区含有 `zephyr` 或 `mcuxsdk`
不代表应从该子目录独立开始本次构建。

### 4.4 `compile_targets`

回答“本次要准备哪类产物”及其候选依赖，不是业务源码目录。
当前分类包括 `flashbin`、`linux`、`m_freertos_sdk`、`zephyr`、`a55_rtos`。

`flashbin` 是编译对象，imx-mkimage 是源码项目，`flash_all` 等是项目 Make target，
这三层不能混为一层。工具依据显式清单或请求工作，不根据目录关联自动编完整链。

### 4.5 `release_packages`

不可通过 Git checkout 切版本的厂商发布包，例如 M 核 SDK 和 SCFW porting kit。
包的版本、板型、来源与校验记录是输入身份的一部分，缺项须明确说明。
不能用名字相近的包、源码目录或历史版本静默替代。

### 4.6 `toolchain` 与 `firmware`

工具链是构建环境输入，固定固件是待消费的二进制输入，二者都不是业务源码仓库。
实际路径、版本和目标支持以本机配置、项目要求与现场核验为准。
固定文件须记录来源；同名文件、目录存在或 hash 一致不自动证明它适配当前板型和软件版本。

## 5. case 与系统生长

### 5.1 Windows 主 case 与 Ubuntu 构建现场

Windows `..\support_level\work\<case>` 是新 case 的唯一主目录。
它不是临时编译缓存，而是后续可理解、可交付和可抽取知识的任务记录容器。
Ubuntu 同名 case 保存源码修改与构建现场；同名不代表路径或文件已经同步。

case 按实际需要使用：

| 内容 | 职责 |
|---|---|
| README | 背景、目标、输入版本、成功判据、结论与交付索引 |
| records | 输入、参数、补丁来源、工具生成记录与过程线索 |
| logs | 命令、串口、USB 和运行观察的原始输出 |
| artifacts | 本次需要留存或交付的产物、补丁、脚本与配置 |
| state | 工具生成的软件状态、待上板产物记录与最小板级观察摘要 |

Windows 留存完整任务上下文，但不为补齐目录下载整棵业务源码或编译缓存。
两端记录应能追溯来源，不把聊天摘要当作原始工程证据。

### 5.2 状态与产物身份

- `software-state` 由构建工具生成，不能手填 hash 或把失败产物标为成功。
- `handoff` 描述待消费的产物、来源、目标与已知前提，不证明板子已经执行过动作。
- `ledger` 保存继续板级操作所需的最小事实和证据引用，不代替原始日志或成为全局状态机。

这些文件按真实任务使用，不为普通讨论或资源查询补齐空目录和状态文件。
取回所需文件时，分别记录 server 原路径与 Windows 落地路径，
核对两端实际大小和 SHA-256 后才用于本地工具。
同一部署组合中的产物不能静默混入其他实验版本。

### 5.3 `to_absorb` 与知识沉淀

可复用的新发现先进入 Windows `..\support_level\to_absorb`，保留来源 case、原始证据、
结论适用范围和建议归属。审阅后再吸收到相关 README、USAGE、关系索引、policy 或工具。

```text
真实任务与原始证据 -> case 中的结论 -> 待审阅发现 -> 长期说明、规则或工具
```

这描述知识来源与维护关系，不是 Agent 每次必须执行的固定步骤。
一次案例不能自动成为全局规则，也不能为吸收结论而改写历史证据。

## 6. 共享基线与 case 工作区边界

共享源码、协同工作区和固定资源用于阅读、对比、版本核对及准备任务输入。
已有其他任务或人工修改的目录不能默认视为干净 release 基线。
需要切换共享源码版本时也须先确认已有修改与使用边界。

任务 patch、编译、生成输出和临时派生在 Ubuntu case 执行现场完成，
不把共享资产长期污染成某一次任务的构建目录。
用户提供的可编辑工作副本按实际授权使用，不擅自覆盖或搬动。

普通 out-of-tree 构建在源码树外执行；
需要 in-tree 构建且命中隔离规则的组件，使用工具准备的 case 隔离源码副本。
复制或准备任务副本时核对来源身份，不能把文件复制与干净 Git checkout 当成等价。

## 7. 板级执行架构

板级操作在 Windows 执行，先确认状态与允许动作，再调用工具。

### 7.1 现场身份与强信号

实际目标板、revision、接口、当前 USB/boot 阶段与授权范围必须现场核验。
BCU、UUU、串口工具与 profile 使用 Windows 版本；历史 Linux 命令不直接执行。
板级历史资料只是限定来源和适用范围的参考，旧 COM、日志和 profile 不代表当前实物。

串口静默不能单独判定整板状态；结合当前 USB、板控和可观察启动证据。
工具调用、串口 READY、收到字节与目标固件已正常运行是不同事实。

### 7.2 动作与证据

会改变板状态的动作前后做 fresh probe，保存原始输出。
写入前确认目标板、介质、本地输入及其身份；未知或不一致时不继续写入。
复位、切 boot mode、写 EEPROM 等动作受真实板型与授权约束，不因接手工作区自动执行。

需要保留 reset 起始日志时，先完成身份识别与串口准备，等待选定 reader READY，再执行已授权的 reset。
动作前后探测是板级操作要求，不是新增的 Agent 调度链。

### 7.3 运行阶段与异构核

传输、写入、进入 U-Boot、启动 Linux、可登录和业务 payload 运行分别保留证据。
不能只凭 UUU 成功或一次串口输出跳过后续阶段判断。

M 核是否已打包、由谁加载、谁管理生命周期、是否满足通信和资源契约分别确认。
板型保留核和资源边界不能按其他板的经验推定。

工具说明见 [Windows 工具入口](../../support_level/tools/README.md)，
板型及历史适用范围见 [板卡资料入口](../../support_level/board_knowledge/README.md)。

## 8. Git、部署与发布边界

### 8.1 轻量仓库与重资产

工作流 Git 只在 Windows 维护，保存允许公开的约定、设计文档、技能、资源说明、
关系索引、机器规则、轻量工具脚本与测试。

业务源码仓库及其 Git 历史留在 Ubuntu；资料、SDK、工具链、固件、镜像和 case
不随工作流发布。本机配置、凭据、内部资料和未经许可的工具二进制同样不公开。
[Git 忽略规则](../../.gitignore)是基础排除，不代替发布前的内容审查。

### 8.2 Windows 部署源与 Ubuntu 运行文件

Windows `server` 目录只维护远端需要的小文件，不存业务资源实体。
部署按当前需要比较并更新目标文件，保留远端人工修改，不整树覆盖或使用删除式同步。
Ubuntu 不部署整个 `workspace`、`.agents`、`.github` 或本工作流 Git。

本地修改、隔离测试通过和正式远端部署是三个不同事实。
远端实际版本、资源是否齐备和工具可用性需要单独核验，不能由本地文档或目录存在推出。
具体范围见 [server 部署说明](../../server/README.md)。

### 8.3 客户交付与发布声明

客户包从当前 case 的证据组织，不是复制内部调试全过程。
Windows 保留组织方法、模板、主 case 和所需交付文件；
Ubuntu 执行需要源码 baseline 的补丁应用与 shell 语义核验。
服务器只部署所需校验脚本，不部署整个技能。

构建、传输、启动与业务验证分别说明；缺失验证不通过打包或 checksum 自动补齐。
具体输入与核验见 [客户包校验器说明](../../server/support_level/tools/build-customer-release/USAGE.md)。

## 9. 文档组织与阅读方式

docs 保存长期设计文档，具体入口见 [docs README](README.md)。
架构文档先共同审阅；施工文档在架构确认后再讨论，不预先把待确认方案写成施工流程。

文档按问题使用，不要求 Agent 按固定顺序通读：

| 问题 | 对应来源 |
|---|---|
| 整体设计、职责和边界是什么 | 本文 |
| 始终需要遵守什么 | [AGENTS.md](../AGENTS.md) |
| 某类任务如何分析和操作 | 对应技能及其按需资料 |
| 某个目录有哪些对象 | 对应 README |
| 项目/工具的具体输入与操作 | 对应 USAGE、清单与 policy |
| 当前机器的路径与连接 | 非公开的本机配置 |

## 10. 核心要点

- 工作区提供领域材料与工程工具，Agent 使用自身的任务与技能机制。
- Windows 维护工作区、操作板子并保存主 case；Ubuntu 保存业务源码与构建现场。
- Windows 的远端部署源不等于 Ubuntu 已部署环境，部署状态需要单独核验。
- 资源项目、编译对象、软件线、发布包和固定输入分别组织，不凭名称相近混用。
- 项目能力、执行校验、产物身份和板级观察分别核对，不能相互代替。
- case 保留任务证据，可复用发现经审阅后进入长期知识与工具。
